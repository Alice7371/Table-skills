# 网页替身：思路与设计框架

旧版 `web-stand-in` 已弃用。本页说明目标、方案分类与设计框架，不是安装或运行指南。

## 1. 目标

减少 Codex 侧总 token 用量，同时减少主任务保留的上下文。

## 2. 先分清几类方案

Skill 是任务选择与操作说明；MCP 是连接工具的一种方式。两者都不天然意味着后台执行、上下文隔离或省 token。应按实际执行位置和结果如何回传分类。

| 类型 | 任务如何执行 | 主任务如何拿到结果 | 核心问题 |
|---|---|---|---|
| A. 结果外包：人工或浏览器自动化 | Codex 准备独立提示词，由人工或浏览器操作交给网页 ChatGPT | 通过对话标识或文件取回答案 | 浏览器稳定性、人工步骤，以及协调和采用成本 |
| B. MCP 任务服务 | Codex 通过工具提交任务，服务管理执行、状态和产物 | 返回任务编号，再查状态或取结果 | 服务是否真的独立运行；工具返回是否足够短 |
| C. 模型后端桥接 | 将网页 ChatGPT 接到宿主的模型调用入口 | 流式回复和工具调用进入原宿主流程 | 替换推理来源与隔离主任务上下文是两件事 |
| D. 原生子任务／subagent | 宿主支持的子任务独立执行，主任务委派并接收结果 | 摘要、结构化结果或产物路径 | 能否减少主任务上下文；子任务用量仍需计入总成本 |

这些方式可以组合。例如，MCP 服务内部仍可能使用浏览器；模型桥接也可能通过 MCP 接回本地工具。判断时看数据流，不只看名称。

## 3. A 类：结果外包

### 设计思路

主任务选出可以独立完成的工作，准备问题、材料范围和交付要求，交给网页 ChatGPT 执行，再取回结果继续工作。交互方式可以是人工复制发送、自动填入后人工发送，或浏览器全自动发送与收取。

### 执行流程

```text
主任务拆出独立工作 → 准备提示词 → 网页 ChatGPT 执行
                                      ↓
主任务采用结果并继续 ← 按任务标识取回答案或产物
```

为每项工作保存唯一标识和对应对话地址，区分已提交、执行中、完成与失败。任务既可在开头分配，也可在长任务过程中按需拆出；如何等待和恢复取决于宿主与收取接口。

### 可能的问题

人工操作可能中断自动流程；浏览器自动化可能受页面变化、连接超时、已有草稿和读取缓存影响。当任务较轻、返回内容较长，或主任务需要重新阅读与论证时，协调和采用结果的成本可能抵消节省的推理。自动收发也不等于任务已经独立运行，需要分别验证。

## 4. B 类：MCP 任务服务

### 设计思路

主任务通过 MCP 工具提交独立工作，由服务管理执行、状态和产物。工具先返回任务编号，主任务可以继续其他工作，在需要结果时查询或收取。MCP 提供连接方式，独立执行能力由服务实现。

### 执行流程

```text
主任务提交工作 → MCP 服务返回任务编号 → 独立执行器处理
       ↓                                      ↓
继续其他工作 → 查询状态或接收通知 → 取回结果并采用
```

接口可分为四项：

| 操作 | 输入 | 输出 |
|---|---|---|
| 提交任务 | 独立问题、材料范围、约束、输出要求、去重标识 | 任务编号和接收状态 |
| 查询状态 | 任务编号 | 排队、执行中、完成、失败或已取消 |
| 取回结果 | 任务编号 | 简短结果、来源、限制、产物路径 |
| 请求取消 | 任务编号 | 是否收到取消请求，以及最终执行状态 |

服务保存任务状态并处理去重和失败恢复，默认只回传必要结论与产物位置。完成通知需要宿主支持；不支持时可按需查询。

### 可能的问题

如果服务只是把长时间阻塞的调用包装成工具，主任务仍可能无法继续。频繁查询或返回大量中间日志，也可能增加 token 和上下文开销。服务内部若使用浏览器，仍需处理页面变化与会话状态；接口固定并不代表执行后端稳定。

## 5. C 类：模型后端桥接

### 设计思路

把网页 ChatGPT 接到宿主的模型调用入口，由桥接层转换请求和返回内容，保留宿主的任务界面及工具流程。可参考 [miuuyy/codex-chatgpt-web](https://github.com/miuuyy/codex-chatgpt-web)：其 README 描述了本地 Responses／SSE 桥接，以及完整模式下通过 MCP 接回当前 Codex 任务工具的方式。本页仅参考其设计，不代表本仓库已实现该能力。

### 执行流程

```text
宿主模型请求 → 桥接层转换 → 网页 ChatGPT 执行
     ↑                           ↓
宿主接收回复与工具调用 ← 桥接层转换返回内容
```

设计时明确发送的上下文范围、宿主任务与网页会话的对应关系、流式返回方式，以及工具调用如何回到原任务。恢复、取消和压缩也需保持任务身份一致。

### 可能的问题

替换模型后端不一定减少主任务上下文，发送完整任务历史还可能增加传输量。使用网页额度与提高 token 效率是不同指标。页面变化、模型不匹配、工具权限和会话恢复都可能影响流程，需要分别验证。

## 6. D 类：原生子任务

### 设计思路

利用宿主提供的子任务或 subagent 接口，把独立工作交给单独的执行上下文。主任务只提供必要材料，接收简短结论和产物位置，再继续后续工作。

### 执行流程

```text
主任务定义子任务与交付要求 → 子任务独立执行
           ↓                       ↓
继续其他工作或等待依赖 ← 收取结论与产物并采用
```

根据任务依赖决定是否并行；指定输入范围、输出要求和文件修改归属，避免多个任务同时覆盖同一文件。等待、取消和恢复方式以宿主实际接口为准。

### 可能的问题

子任务可能重复加载指令或材料，增加总 token；回传完整过程也可能挤占主任务上下文。依赖关系、修改冲突或交付不完整可能导致返工。子任务若运行在 Codex 侧，其用量需要一并核算。

## 7. 后续统一的设计与验收框架

设计时分成四层：

1. **选任务**：材料可独立提供、计算或推理足够重、输出紧凑且能直接采用。短问答、已经读过的资料、反复依赖本地代码的工作通常不合适。
2. **管执行**：为任务分配唯一编号，保存状态；明确一次提交、失败恢复、取消及重复收取的规则。网络超时不能直接当作提交失败后再发一次。
3. **回结果**：返回结论、必要证据、限制与产物位置。原始内容按需读取，重要的不确定性不能为了缩短答案而删去。
4. **算完整账**：从提交前算到结果已被主任务采用，同质量、同任务比较，而不是只看网页生成阶段。

| 验证项 | 判定方式 |
|---|---|
| Codex 侧总 token | 所有参与执行的 Codex 调用累计输入加输出；推理 token 若已包含在输出中，不重复相加 |
| 主任务上下文 | 比较完成结果采用后，主任务实际保留或再次输入的上下文；不拿累计输入量代替上下文大小 |
| 稳定性 | 记录成功、失败、重试、人工介入和耗时，失败样本也计入评估 |
| 任务完成度 | 结果满足原要求，来源和必要限定保留；不能靠少做任务制造节省 |

网页端用量不计入本项目的 Codex 侧核算，但应说明执行来源。缓存输入、非缓存输入、推理输出用于解释差异；不能只挑下降的指标。只有总 token 和主任务上下文均降低，才算同时满足原始目标。

开发调试、功能探测与正式对照分开记录；演示用数字不能用于验收。后续若有新实现，先验证一个可重复的完整任务，再决定是否恢复为可安装 Skill。
